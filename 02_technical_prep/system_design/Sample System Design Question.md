We have a third-party application sending us real-time event logs via public webhooks. We expect massive traffic spikes during marketing campaigns. We need to process this data, aggregate total event counts by source on a daily level, and expose these insights to an internal analytics dashboard. Design this end-to-end.

## Ingestion Layer
1. Propose using **AWS API Gateway** to receive the webhooks, which immediately handles incoming public traffic safely. You back it with a lightweight **AWS Lambda** function.
2. Instead of writing the data straight to a heavy database (which could crash under a spike), you explain that Lambda validates the token and immediately drops the raw JSON payload into **Amazon S3** or pushes it into an **Amazon SQS queue**. This decouples the system and guarantees you won't drop events.

## Storage and Lakehouse Transition
- **Question:** The data is sitting in S3 as raw, unstructured JSON. How do we structure it for downstream analytics?
	- **Answer:** Suggest an ELT (Extract, Load, Transform) pattern over a legacy ETL dump. ELT is preferred because the data is unstructured. ETL requires the data to be structured before loading. ELT provides more flexibility to backfill and re-run the unstructured data through the pipeline in the event software bugs corrupt data. You choose **Databricks and PySpark** (or Snowflake) to run distributed transformation jobs. You explicitly state you will enforce **Schema Evolution** to catch schema drift if the webhook payload formats change. You will save the data into a **Delta Lake / Parquet** format partitioned by date and event_source to optimize query performance.

## Handling Edge Cases
- **Question:** We deployed a bug yesterday that messed up our PySpark aggregation logic for the past 24 hours. The raw data in S3 is fine, but our analytics dashboard is showing corrupted metrics. How do you fix this?
	- **Answer:** Because our architecture decouples ingestion from compute, fixing this is a straightforward **backfill operation**. First, I would patch the bug and push the corrected aggregation script through our CI/CD pipeline. Next, I would leverage the **idempotent design** of our Databricks pipeline. Because our target table uses a MERGE or an OVERWRITE partition strategy based on the event date, I can simply spin up a Spark cluster and re-run the pipeline specifically targeted at the raw S3 bucket location for the last 24 hours. The new run will safely overwrite the corrupted 24-hour block without duplicating records or generating partial data.
		- **Idempotency:** This is a golden word in data engineering. An idempotent pipeline means **no matter how many times you run it with the same input data, you will always get the exact same result**. If your pipeline just used basic INSERT statements, re-running it would double-count everything and create a nightmare. By using a target table strategy that overwrites data by date, your pipeline is self-healing.
		- **Backfilling:** This is the formal term for running historical data through a new or corrected pipeline. Mentioning that you would target _only_ the specific 24-hour partition shows that you are cost-conscious and understand distributed computing performance—you aren't wasting money processing 3 years of data just to fix 1 day.
